# Архитектура

## Общая схема

```text
Пользователь
  |
  v
Claude Desktop
  |
  | MCP / stdio
  v
MCP Server
  |
  +--> DataTools
  |      |
  |      +--> LoadingSkill
  |      +--> ProfilingSkill
  |      +--> CleaningSkill
  |
  +--> AnalysisTools
  |      |
  |      +--> AnalysisSkill
  |
  +--> VisualizationTools
         |
         +--> VisualizationSkill
                   |
                   +--> AnalysisSkill

Все компоненты работают с одним общим DatasetRegistry.
```

Приложение представляет собой локальный однопроцессный MCP Server. Claude
Desktop запускает его как дочерний процесс и обменивается данными через
stdin/stdout. Реализация разделена на границу MCP, тонкие адаптеры tools,
skills предметной области и хранилище в памяти.

## LLM как оркестратор

Запрос пользователя определяет, какие виды анализа полезны. LLM изучает профиль
набора, выбирает tools и их параметры, запрашивает точные вычисления и
преобразует структурированные результаты в связный текст. Единого жестко
заданного конвейера анализа намеренно нет.

Такой подход сохраняет гибкость интерпретации, не делая вычисления
вероятностными. Python отвечает за арифметику, статистику, сортировку, очистку,
корреляции и создание графиков. LLM отвечает за понимание намерения,
последовательность вызовов, выбор измерений и объяснение.

## MCP как граница внешнего интерфейса

MCP — единственный внешний интерфейс приложения. `src.server` регистрирует
восемь операций, преобразует ожидаемые ошибки предметной области в понятные ошибки MCP tools
и возвращает поддерживаемые SDK Pydantic-модели. Сервер не содержит
специфичной для Claude бизнес-логики, поэтому те же tools может использовать другой
MCP-совместимый клиент.

Транспорт stdio также задает строгое правило вывода: stdout принадлежит
протоколу. Диагностика должна использовать стандартный logging, направленный в
stderr.

## Tools и skills

**Tool** — публичная операция, доступная LLM. Tool adapters предоставляют
небольшой стабильный API, например `load_data`, `aggregate_data` или `plot_bar`.

**Skill** содержит переиспользуемую реализацию предметной логики. Skills проверяют
состояние набора и столбцы, работают с pandas или matplotlib и создают
типизированные результаты. Они не импортируют MCP и не зависят от него. Поэтому
их легко тестировать напрямую, а изменения framework не проникают в код
аналитики.

Направление зависимостей одностороннее:

```text
MCP server -> tools -> skills -> storage/libraries
```

## Состояние набора и `dataset_id`

Pandas DataFrame остается внутри server process. Передача DataFrame через MCP
создала бы большие, зависящие от реализации и часто не совместимые с JSON
payloads. Вместо этого `load_data` сохраняет DataFrame в `DatasetRegistry` и
возвращает непрозрачный UUID-based `dataset_id`. Публичные результаты содержат
только компактные JSON-совместимые metadata, вычисленные значения и пути к
графикам.

Каждая группа tools должна получить один и тот же экземпляр `DatasetRegistry`.
Иначе набор, загруженный через `DataTools`, был бы недоступен для
`AnalysisTools` или `VisualizationTools`. Поэтому `src.server` создает один
общий registry приложения и передает его всем трем группам. `create_server`
создает эквивалентную изолированную сборку для тестов.

Registry использует defensive copies DataFrame, а cleaning заменяет сохраненный
DataFrame под тем же ID. Поскольку storage находится в памяти, после завершения
процесса сервера все IDs становятся недействительными.

## Детерминированные вычисления

Все числовые утверждения происходят из операций Python:

- pandas рассчитывает профили, агрегации, median и корреляции Pearson;
- cleaning применяет явные и воспроизводимые правила;
- расчет корреляций исключает диагональ и повторные пары, сохраняя знак значения;
- matplotlib строит графики из тех же структурированных значений, которые
  возвращаются клиенту.

Такое разделение не позволяет внешней LLM оценивать суммы или значения графиков
приблизительно. LLM может объяснять корреляцию, но не должна представлять ее
как причинность.

## Очистка и выбросы

Очистка намеренно консервативна. Точные повторяющиеся строки можно удалить, числовые
пропуски заполнить median, а категориальные и boolean значения — mode, если тип
это допускает. Пропущенные datetime остаются без изменений: искусственные даты
не создаются.

Числовые выбросы обнаруживаются методом IQR и попадают в отчет, но не удаляются.
Экстремальное значение может быть реальной транзакцией или бизнес-событием;
автоматическое удаление незаметно изменило бы исходные данные. LLM или
пользователь могут решить, требуется ли дальнейшее исследование.

## Результаты визуализации

Графики сохраняются как локальные PNG, но каждый результат визуализации также
содержит структурированные числовые данные. Результат trend включает нанесенные
периоды и сводные значения, bar chart — точные сгруппированные строки,
distribution — статистику и количество значений по интервалам, а
`correlation_analysis` — полную матрицу и сильнейшие пары.

PNG предназначен для просмотра человеком. Структурированные значения служат
источником числовых утверждений LLM.

## Почему финальный текст создает внешняя LLM

Сервер намеренно не вызывает LLM и не содержит жестко заданных рекомендаций.
Содержание отчета зависит от запроса пользователя и контекста разговора. Claude
Desktop уже предоставляет эту возможность, поэтому ее дублирование внутри
skill добавило бы учетные данные, стоимость и связанность, не улучшив
детерминированный анализ.

## Жизненный цикл запроса

1. Claude вызывает `load_data` с локальным путем к CSV или XLSX.
2. Loading skill разбирает типы, сохраняет DataFrame и возвращает `dataset_id`.
3. Claude повторно использует этот ID для профилирования и при необходимости
   очистки.
4. Skills анализа и визуализации получают актуальный DataFrame из registry.
5. Tools возвращают компактные Pydantic results; результаты графиков также
   содержат локальные пути к PNG.
6. Claude формирует итоговое объяснение из вычисленных фактов.

## Точки расширения

Текущей композиции зависимостей достаточно; plugin или skill registry добавил
бы лишнюю сложность без практической пользы. Новую возможность можно добавить
небольшими шагами:

1. Добавить или расширить Pydantic result schema, если нужен новый публичный
   контракт.
2. Реализовать независимый от framework skill с внедренным `DatasetRegistry`.
3. Добавить тонкий метод в подходящий tool adapter.
4. Зарегистрировать MCP handler в `src.server` с ясным описанием для модели.
5. Добавить прямые тесты skill и проверку MCP wiring.

Те же границы позволяют в будущем добавить постоянное или объектное хранилище
наборов, registries на уровне сессий, фоновое выполнение, удаленный транспорт
MCP, более развитый выбор графиков, записи аудита и экспорт отчетов, не перенося
логику аналитики в слой MCP.
